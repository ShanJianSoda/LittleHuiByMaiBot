# MaiBot 完整生命周期与 src 模块示例

本文档描述从启动到单条消息处理、再到关闭的完整生命周期，并标明 **src/** 下每个文件夹（除 dream、mood、webui）在流程中的职责与调用关系。示例中的类名、函数名、文件路径均与代码一致，便于对照与校验。

---

## 一、src 下各文件夹功能概览（除 dream / mood / webui）

| 文件夹 | 功能简述 | 在生命周期中的体现 |
|--------|----------|--------------------|
| **config** | 配置加载与访问：`global_config`、`model_config`，从 toml 与环境变量读取 | 启动时加载；消息过滤、回复、LLM、知识库等处处使用 |
| **common** | 基础设施：日志、消息 API、Server、数据库、消息仓储、遥测、TCP 连接、数据模型 | 启动时初始化 API/Server/DB；消息存储与查询；定时遥测 |
| **chat** | 聊天主流程：消息接收、心流/脑聊、规划、回复、知识库、表情、统计等 | 从收消息到生成并发送回复的全链路 |
| **bw_learner** | 表达学习：表达方式学习/反思/自动检查、消息记录与分发 | 回复前/后参与表达学习与反思 |
| **llm_models** | LLM 请求封装：`LLMRequest`、各 model client、payload 等 | 规划、回复、知识库、表情、统计等所有调用 LLM 的地方 |
| **manager** | 异步任务与本地存储：`async_task_manager`、`local_storage` | 启动时注册定时任务；遥测等使用 local_storage |
| **memory_system** | 记忆与检索：聊天摘要、记忆检索 prompt、检索工具（人物/知识/历史等） | 回复时构建记忆检索块；心流中聊天摘要后台运行 |
| **person_info** | 用户/关系信息：`Person`、`register_person`、关系与称呼 | 消息处理时注册用户；回复时用于称呼与 action 记录 |
| **plugin_system** | 插件框架：插件加载、事件、组件注册、各类 API（generator/send/message/database 等） | 启动时加载插件；消息前后事件、命令、Action、Tool |
| **plugins** | 内置插件与知识：表情、插件管理、TTS、LPMM 知识等 | 作为插件被 plugin_system 加载并注册组件 |

## 二、完整生命周期：从启动到一条消息回复再到关闭

以下按时间顺序，用「阶段 + 涉及模块」的方式描述一条消息从进入到回复发送、以及系统关闭的完整路径。每个括号内标明 **src 下的文件夹** 或具体文件，便于在代码中定位。

---

### 阶段 0：进程入口与最早初始化（bot.py，非 src 内）

- **bot.py** 作为入口：
  - 加载 `.env`（`dotenv`）、设置工作目录、`initialize_logging`。
  - Runner/Worker 进程区分（`MAIBOT_WORKER_PROCESS`）。
  - Worker 中：`raw_main()` → 检查 EULA → 创建 `MainSystem()`，`asyncio.run(main_system.initialize())` 与 `main_system.schedule_tasks()`。
- 此时尚未进入 **src/main.py**，但会调用 **src/common/logger** 的 `initialize_logging`、`get_logger`。

---

### 阶段 1：MainSystem 初始化（src/main.py）

- **src/main.py** 中 `MainSystem.__init__`：
  - 使用 **src/common/message** 的 `get_global_api()` 得到 `MessageServer`（即 `self.app`）。
  - 使用 **src/common/server** 的 `get_global_server()` 得到 `Server`（FastAPI + Uvicorn）。
  - 若启用 WebUI，则在此设置 `webui_server`（此处不展开 webui 逻辑）。
- **src/config**：在导入链中会加载 **src/config/config.py** 的 `global_config` 等，供全局使用。

---

### 阶段 2：异步初始化 _init_components（src/main.py）

`await system.initialize()` 内部调用 `_init_components()`，顺序大致如下：

1. **src/manager**  
   - `async_task_manager.add_task(OnlineTimeRecordTask())`  
   - `async_task_manager.add_task(StatisticOutputTask())`  
   - `async_task_manager.add_task(TelemetryHeartBeatTask())`  
   - `async_task_manager.add_task(ExpressionAutoCheckTask())`  
   - 其中：`OnlineTimeRecordTask` / `StatisticOutputTask` 来自 **src/chat/utils/statistic**；`TelemetryHeartBeatTask` 来自 **src/common/remote**；`ExpressionAutoCheckTask` 来自 **src/bw_learner**。  
   - **src/manager/local_store_manager** 的 `local_storage` 会被 **src/common/remote** 的遥测任务使用（如 UUID、部署时间等）。

2. **src/chat/knowledge**  
   - `lpmm_start_up()`：若启用 LPMM，则初始化 **src/chat/knowledge** 的 EmbeddingManager、KGManager、QAManager（依赖 **src/config**、**src/llm_models**）。

3. **src/plugin_system**  
   - `plugin_manager.load_all_plugins()`：插件目录由 `_ensure_plugin_directories()` 默认包含 `src/plugins/built_in` 与项目根 `plugins`，从中加载插件（即 **src/plugins** 下的 built_in 与用户插件），注册 Command/Action/Tool/EventHandler 等到 **src/plugin_system/core/component_registry**。

4. **src/chat/emoji_system**  
   - `get_emoji_manager().initialize()`：初始化表情包管理器（会用到 **src/common/database**、**src/llm_models** 等）。

5. **src/chat/message_receive**  
   - `get_chat_manager()._initialize()`：初始化 **src/chat/message_receive/chat_stream** 的 ChatManager（会使用 **src/common/database**、**src/common/database/database_model** 的 ChatStreams 等）。  
   - `asyncio.create_task(get_chat_manager()._auto_save_task())`：后台自动保存聊天流。

6. **src/main.py** 将 **src/chat/message_receive/bot** 的 `chat_bot.message_process` 注册到 **src/common/message** 提供的 API：  
   - `self.app.register_message_handler(chat_bot.message_process)`  
   - `self.app.register_custom_message_handler("message_id_echo", chat_bot.echo_message_process)`  

7. **src/plugin_system**  
   - `events_manager.handle_mai_events(EventType.ON_START)`：触发插件系统的「启动」事件。

至此，**config / common / chat / bw_learner / llm_models / manager / memory_system / person_info / plugin_system / plugins** 均已在启动链中出现（memory_system 的检索 prompt 初始化可能在 replyer 首次使用时触发，见阶段 5）。

---

### 阶段 3：调度常驻任务（src/main.py）

- `schedule_tasks()` 中 `asyncio.gather(...)` 包含：
  - **src/chat/emoji_system**：`get_emoji_manager().start_periodic_check_register()`
  - **src/dream**：`start_dream_scheduler()`；dream 整理 ChatHistory 时可通过工具写入关系记忆（见第六节）。
  - **src/common/message** 对应的 `self.app.run()`（接收外部消息并回调 `message_process`）
  - **src/common/server**：`self.server.run()`（FastAPI 服务）
  - 若启用 WebUI，则还有 webui_server.start()

---

### 阶段 4：收到一条消息 —— 从 API 到心流/脑聊入口

1. **common**  
   - 消息由 **src/common/message** 的 MessageServer（app）接收，并调用已注册的 `chat_bot.message_process(message_data)`。

2. **src/chat/message_receive/bot**  
   - `message_process`：
     - 使用 **src/config** 的 `global_config` 做平台/用户等解析。
     - 构建 **src/chat/message_receive/message** 的 `MessageRecv(message_data)`。
     - **src/plugin_system**：`events_manager.handle_mai_events(EventType.ON_MESSAGE_PRE_PROCESS, message)`。
     - 若为通知消息，`handle_notice_message` 处理后返回。
     - `message.process()` 解析内容、生成 `processed_plain_text` 等。
     - **src/config**：`_check_ban_words` / `_check_ban_regex` 过滤。
     - **src/chat/message_receive/chat_stream**：`get_chat_manager().register_message(message)`，`get_or_create_stream(...)`，`message.update_chat_stream(chat)`。
     - **src/plugin_system**：命令处理 `_process_commands(message)`（**component_registry.find_command_by_text**，执行 Command，可能拦截）。
     - **src/plugin_system**：`events_manager.handle_mai_events(EventType.ON_MESSAGE, message)`。
     - **src/chat/utils/prompt_builder**：若有模板信息，`global_prompt_manager.async_message_scope`。
     - 最后调用 **src/chat/heart_flow/heartflow_message_processor** 的 `HeartFCMessageReceiver.process_message(message)`。

3. **src/chat/heart_flow/heartflow_message_processor**  
   - `process_message` 中：
     - **src/chat/utils**：`is_mentioned_bot_in_message`、**src/chat/utils/chat_message_builder** 的 `replace_user_references`。
     - **src/chat/message_receive/storage**：`MessageStorage.store_message(message, chat)` → 写入 **src/common/database/database_model** 的 Messages、Images 等。
     - **src/chat/heart_flow/heartflow**：`heartflow.get_or_create_heartflow_chat(chat.stream_id)`。
     - **src/person_info**：`Person.register_person(...)`（登记用户/群内昵称等）。
   - 群聊得到 **src/chat/heart_flow/heartFC_chat** 的 `HeartFChatting`，私聊得到 **src/chat/brain_chat** 的 `BrainChatting`（二者均由 **src/chat/heart_flow/heartflow** 创建并缓存）。

4. **src/chat/heart_flow/heartFC_chat**（以群聊为例）  
   - 若尚未启动：`start()` 中启动 `_main_chat_loop()` 以及 **src/memory_system/chat_history_summarizer** 的 `ChatHistorySummarizer(stream_id).start()`。  
   - 主循环中根据频率与 @ 决定是否进入 `_observe(...)`（**src/chat/heart_flow/frequency_control** 参与决策）。

---

### 阶段 5：一次「观察」与回复生成（心流内）

在 `HeartFChatting._observe` 中（仍以群聊为例）：

1. **src/bw_learner**  
   - **expression_reflector**：`reflector.check_and_ask()`。  
   - **reflect_tracker**：`tracker.trigger_tracker()`，若解析则移除 tracker。  
   - **message_recorder**：`extract_and_distribute_messages(stream_id)` 向 expression_learner、jargon_miner 等分发消息。

2. **src/chat/planner_actions**  
   - **action_modifier**：`modify_actions()`（可能调用插件等）。  
   - **action_manager**：`get_using_actions()`。  
   - **planner**：`ActionPlanner` 使用 **src/llm_models** 的 `LLMRequest`（planner 用）生成规划结果。

3. **src/chat/utils/chat_message_builder**  
   - `get_raw_msg_before_timestamp_with_chat` 等会调用 **src/common/message_repository** 的 `find_messages`。  
   - `build_readable_messages_with_id` 等构建给 LLM 的对话块。

4. **src/memory_system**  
   - **memory_retrieval**：在 **src/chat/replyer**（group_generator / private_generator）中调用 `build_memory_retrieval_prompt`，使用 **memory_system** 的检索工具与 prompt（**memory_retrieval**、**retrieval_tools**、**memory_utils**）。  
   - **chat_history_summarizer**：已在阶段 4 随 HeartFChatting 启动，后台做摘要与话题压缩（使用 **src/llm_models**）；在成功写入 ChatHistory 后，若启用关系功能，会为参与者写入关系记忆（**person_info** 的 `store_person_memory_from_answer`），见第六节。

5. **src/chat/replyer**  
   - 群聊：**group_generator**；私聊：**private_generator**。  
   - 使用 **src/llm_models** 的 `LLMRequest`（replyer 用）、**src/chat/replyer/prompt** 下模板、**memory_system** 的记忆检索块、**src/chat/knowledge** 的 LPMM 知识（若启用）等生成回复内容。  
   - **关系系统（读）**：若启用关系功能，replyer 以轻量方式为当前发送者构建关系信息块（**person_info** 的 memory_points），传入回复模板的 `relation_info_block`，群聊与私聊均适用。  
   - **src/chat/replyer/replyer_manager** 负责在不同场景下选用 group/private generator。

6. **src/chat/heart_flow/heartFC_chat**  
   - `_send_response` / `_send_and_store_reply`：通过 **src/plugin_system/apis** 的 `send_api` 等发送；  
   - **src/person_info**：`Person(...).person_name` 用于 action 展示；  
   - **src/plugin_system/apis/database_api**：`store_action_info` 等。  
   - **src/chat/message_receive/storage**：存储发出的消息（再次用到 **src/common/database**、**database_model**）。

7. **src/bw_learner**  
   - 回复过程中或之后，**expression_learner**、**expression_selector**、**jargon_miner** 等会参与表达学习与术语挖掘（**message_recorder** 已把消息分发给它们）。

至此，**config / common / chat / bw_learner / llm_models / manager / memory_system / person_info / plugin_system / plugins** 在「一条消息的回复」链路上都已有体现。

---

### 阶段 6：定时任务中的模块体现

- **src/chat/utils/statistic**：`OnlineTimeRecordTask`、`StatisticOutputTask` 使用 **src/common/database**、**database_model**（如 OnlineTime、LLMUsage、Messages）。  
- **src/common/remote**：`TelemetryHeartBeatTask` 使用 **src/manager/local_store_manager**、**src/config**、**src/common/tcp_connector**（如 aiohttp 请求）。  
- **src/bw_learner/expression_auto_check_task**：`ExpressionAutoCheckTask` 使用 **src/common/database/database_model**（Expression）、**src/config**、**src/llm_models** 做表达方式自动检查。

---

### 阶段 7：关闭与清理（bot.py）

- 收到 KeyboardInterrupt 后，`graceful_shutdown()`：
  - **src/plugin_system**：`events_manager.handle_mai_events(EventType.ON_STOP)`。  
  - **src/manager**：`async_task_manager.stop_and_wait_all_tasks()`。  
  - 取消剩余 asyncio 任务、关闭事件循环、**src/common/logger** 的 `shutdown_logging()`。

## 五、常见问题说明

### 5.1 `template_group_name` 是干什么用的？（bot.py:329-331）

**作用：按「消息」或「会话」切换一套独立的 prompt 模板，让同一条麦麦在不同渠道/会话里用不同人设或话术。**

- **来源**：当消息来自「带自定义模板信息的接口」时，`message.message_info.template_info` 里会有 `template_name`（模板组名）和 `template_items`（名 → 内容）。此时 `template_group_name = template_info.template_name`；否则为 `None`（用全局默认模板）。
- **第一处（315-322 行）**：若有 `template_group_name`，在 `async_message_scope(template_group_name)` 下，把 `template_items` 里每个名字对应的内容用 `Prompt.create_async(...)` 注册到**该作用域**，相当于「这一组消息用的专属 prompt」。
- **第二处（329-331 行）**：调用 `preprocess()`（即 `heartflow_message_receiver.process_message`）时，若存在 `template_group_name`，同样在 `async_message_scope(template_group_name)` 里执行。这样从「收消息」到后续心流里 `_observe` 时，`chat_stream.context.get_template_name()` 会返回同一个名字；心流、回复器里通过 `global_prompt_manager.get_prompt_async(name)` 取 prompt 时，会**先查当前作用域**，于是拿到的是**这条消息/这个会话绑定的那套模板**，而不是全局默认。
- **总结**：`template_group_name` = 「这一条消息（或这一会话）用哪一组 prompt 模板」。用于多渠道/多会话下「同一套代码、不同人设或话术」的场景。

### 5.2 组件类型（ComponentType）设计是什么意思？

插件可以向麦麦注册多种**组件**，每种组件有固定**类型**，核心按类型来**分发**谁处理、何时触发。`ComponentType` 就是这些类型的枚举。

| 类型 | 含义 | 谁触发 / 何时用 | 典型用法 |
|------|------|------------------|----------|
| **ACTION** | 动作：麦麦「这一轮可以执行的一类操作」 | Planner（LLM）根据当前对话选一个或多个动作，再执行 | 发问候、查知识库、发表情包等 |
| **COMMAND** | 命令：用户发**固定格式**时直接执行 | 用户消息匹配 `command_pattern`（如 `/time`）时，由 `component_registry.find_command_by_text` 找到并执行 | `/time`、`/test`、`/random_emojis` |
| **TOOL** | 工具：LLM 在生成回复过程中可**调用**的函数 | 回复器把工具列表给 LLM，LLM 返回 tool_calls；框架执行对应 Tool 的 `execute` | 比较数字、查 LPMM 知识、查天气等 |
| **EVENT_HANDLER** | 事件处理：在**生命周期某时刻**统一回调 | `events_manager.handle_mai_events(EventType.xxx)` 时，所有注册了该事件的 Handler 被调用 | ON_MESSAGE 时改消息、ON_START 时初始化等 |
| **SCHEDULER** | 定时任务（预留） | 暂无实现 | 预留 |

**设计要点**：

1. **一个插件可以注册多种类型**：例如同一个插件里既有 Command（如 `/time`），也有 Action（如「问候」）、Tool（如「比较两数」）、EventHandler（如「收到消息时打印」）。
2. **核心按类型分发**：
   - 用户发消息 → 先看是不是 Command（文本匹配）→ 不是再走心流；心流里 Planner 从 **ACTION** 里选动作执行；生成回复时 LLM 可调 **TOOL**；消息到达/发送等时机触发 **EVENT_HANDLER**。
3. **命名空间**：注册时用 `component_type + 组件名`（如 `action.hello_greeting`、`command.time`）避免不同类组件同名冲突。

**和文档示例的对应关系**：文档里「命令处理」「Action」「Tool」「ON_MESSAGE 事件」等，指的就是上述 COMMAND / ACTION / TOOL / EVENT_HANDLER 在一条消息从进入到回复发出这条链路上的不同触发点；示例中的 `find_command_by_text`、`get_using_actions`、`generator_api.generate_reply`（内部会传 tools）、`handle_mai_events(ON_MESSAGE)` 就是按类型分发的具体实现。

### 5.3 话题（Topic）与 ChatHistory 的完整生命周期

「话题」相关数据分两层：**进行中话题缓存**（仅 Summarizer 内部）和**已落库的 ChatHistory 表**。记录（写）与读取（读）的完整路径如下。

#### 5.3.1 进行中话题缓存（topic_cache / current_batch）

| 环节 | 位置 | 说明 |
|------|------|------|
| **写** | **src/memory_system/chat_history_summarizer.py** | `process()` 被定时循环调用 → 新消息进入 `current_batch`；满足条件时 `_check_and_run_topic_check` → `_run_topic_check_and_update_cache`：LLM 识别话题，更新内存中的 `topic_cache`（topic → TopicCacheItem），并调用 `_persist_topic_cache()` 将 topic_cache 与 current_batch 的时间范围写入**本地 JSON**（`data/hippo_memorizer/{chat_id}.json`）。 |
| **读** | **同一 summarizer 实例内** | 启动时 `_load_topic_cache_from_disk()` 从上述 JSON 恢复 `topic_cache`；`_load_batch_from_disk()` 恢复 `current_batch`。每次 `_run_topic_check_and_update_cache` 内用 `existing_topics = list(self.topic_cache.keys())` 做话题匹配与合并。**不对外暴露**，仅用于本 chat 的后续话题聚合与打包。 |

#### 5.3.2 已打包的 ChatHistory 表（database）

| 环节 | 位置 | 说明 |
|------|------|------|
| **写** | **ChatHistorySummarizer** | `_finalize_and_store_topic`（话题满足打包条件后）→ `_store_to_database` → **database_api.db_save(ChatHistory, data)**，写入 **ChatHistory 表**（theme、summary、keywords、key_point、participants、start_time、end_time 等）。 |
| **写** | **Dream** | **src/dream/tools/create_chat_history_tool.py**、**update_chat_history_tool.py**：模型在整理时调用 create/update 工具，同样写入 **ChatHistory 表**。 |
| **读** | **记忆检索（回复时）** | **src/memory_system/memory_retrieval.py**：`build_memory_retrieval_prompt` 被 group/private generator 调用 → 内部运行 ReAct 查询；若 LLM 选择调用工具，则执行 **src/memory_system/retrieval_tools/query_chat_history.py** 的 `search_chat_history(chat_id, keyword, participant, ...)` 与 `get_chat_history_detail(chat_id, memory_ids)`。二者通过 **ChatHistory.select()** 等查询同一张 **ChatHistory 表**，结果拼入记忆检索字符串，最终作为 `memory_retrieval` 块传入回复 prompt。**chat_id 由 memory_retrieval 在调用工具时注入**（见 memory_retrieval.py 中 `sig.parameters` 含 `chat_id` 时写入 `tool_params["chat_id"]`）。 |
| **读** | **Dream** | **src/dream/tools/search_chat_history_tool.py**、**get_chat_history_detail_tool.py**：dream agent 整理时调用上述工具，同样从 **ChatHistory 表** 按 chat_id 查询；**dream_agent.py** 中 `_pick_random_memory_for_chat`、`_pick_random_chat_id` 等用 `ChatHistory.select()/get_or_none()` 选起始记忆或统计 chat。 |

#### 5.3.3 小结：话题相关「读」在哪里

- **话题缓存（未落库）**：只在 **ChatHistorySummarizer** 内部读写——读在 `_load_topic_cache_from_disk` 与 `_run_topic_check_and_update_cache` 中对 `topic_cache` 的使用，不对外提供接口。
- **ChatHistory 表（已落库）**：读入口有两处——  
  1）**记忆检索**：`build_memory_retrieval_prompt` → ReAct 工具 `search_chat_history` / `get_chat_history_detail`（**query_chat_history.py**）→ 查表，结果用于生成回复；  
  2）**Dream**：dream 的 search/get 工具与选起始记忆逻辑查表，用于整理与调度。

按上述路径在仓库中搜索 `topic_cache`、`ChatHistory.select`、`search_chat_history`、`get_chat_history_detail` 即可对照实现。

## 六、关系系统整合方案（群聊与私聊均生效）

关系系统包含两条链路：**写**（新增/更新 Person 的 memory_points）与**读**（回复时注入关系信息块）。原实现仅在私聊回复链中通过 `build_relation_info` 读关系，且因耗时长、耗 token 被注释；写链路 `store_person_memory_from_answer` 已实现但无调用方。下面说明如何将关系系统与完整生命周期结合，并让群聊和私聊都生效。

### 6.1 在生命周期中的位置

| 阶段 | 关系系统参与方式 |
|------|------------------|
| **阶段 4（收消息）** | **person_info**：`Person.register_person` 登记用户；不直接写关系，但为后续「写关系」提供 person_id / is_known 等基础。 |
| **阶段 5（回复生成）** | **读关系**：在 **replyer**（group_generator / private_generator）中，用**轻量**方式为当前发送者构建 `relation_info_block`（见 6.3），不在此处做关系**写入**，避免回复链变重。 |
| **阶段 5 后台 / 定时** | **写关系（入口 1）**：**memory_system/chat_history_summarizer** 在 `_store_to_database` 成功写入 ChatHistory 后，若开启关系功能，对本次概括的 `participants` 中每位已知用户调用 **person_info** 的 `store_person_memory_from_answer`，把本段话题的 summary/key_point 沉淀为关系记忆。Summarizer 按 chat_id 运行，**群聊与私聊**都会跑，故两边都会自动写关系。 |
| **阶段 3 定时任务** | **写关系（入口 2）**：**dream** 调度器定期对某 chat_id 的 ChatHistory 做整理。在 **dream** 中新增工具（如 `store_person_relation`），内部调用 `store_person_memory_from_answer`；模型在整理/合并记忆时，若发现「关于某参与者的可沉淀事实」，可主动调用该工具。Dream 按 chat_id 整理，**群聊与私聊**的 ChatHistory 都可能被整理，故两边都能通过 dream 写关系。 |

结论：**写**放在 **Summarizer（自动）** 与 **Dream（模型调工具）**，不放在回复链；**读**放在 **replyer**，用轻量方式为当前发送者取关系，群聊和私聊统一走同一套逻辑。

### 6.2 为何选 Summarizer + Dream，有无更合适选择

- **Summarizer**：已在阶段 4 随 HeartFChatting/BrainChatting 启动，定期把**当前聊天流**打成 ChatHistory，天然有 `participants`、`summary`、`key_point`。在写入 ChatHistory 后顺带为参与者写关系，**不增加额外请求**，且群聊/私聊都有 summarizer，覆盖全面。替代方案：在「每条消息存储后」立刻写关系——会非常频繁、难以做话题级聚合，且易重复；不如话题打包后写一次。
- **Dream**：定期对**已有 ChatHistory** 做合并、重写、删除，模型能看到参与者和概括内容。在整理过程中由模型**主动**调用 `store_person_relation`，适合「从多条概括里提炼出关于某人的一条精炼关系」的场景，与「整理记忆」的心智一致。替代方案：仅靠 Summarizer 自动写——实现简单但无法做「合并多条再写一条」的提炼；dream 工具可补足这一块。

因此：**Summarizer（自动写）+ Dream（工具写）** 是当前架构下较合适的选择；没有更合适且未覆盖的入口需要单独为关系再开一条管线。

### 6.3 回复时「读关系」：轻量方案（群聊与私聊统一）

原先 `build_relation_info` 会调 LLM（relation_selection_model）做分类选择再按分类取 memory，导致耗时长与 token 增加。若要**群聊和私聊都生效**且不拖慢回复，建议：

- **轻量读**：不调 LLM，仅从 `Person(sender).memory_points` 中按分类或随机取若干条，格式化为 `relation_info` 字符串，传入现有的 `relation_info_block`。私聊的发送者唯一；群聊取当前消息发送者，对该发送者同样做一次轻量读。这样 **private_generator** 与 **group_generator** 都可增加/恢复「构建 relation_info」这一步，但用轻量实现，避免回复链再调 LLM。
- **可选恢复 LLM 选分类**：若配置需要「按当前聊天内容选相关分类再取记忆」，可将原 `build_relation_info` 作为可选路径（如 `relationship.use_relation_llm_selection`），仅在开启时在私聊或群聊中执行，并接受额外耗时与 token。

实现要点：

- 在 **person_info** 中提供同步方法，例如：给定 `person_name`，返回「该人 memory_points 的轻量摘要字符串」（不调 LLM，如每类取 1 条或总共取 N 条）。
- **private_generator**：恢复或新增「构建 relation_info」任务（轻量版），结果仍写入 `results_dict["relation_info"]`，并传入 `relation_info_block`（当前模板已支持）。
- **group_generator**：在并行任务中增加对**当前发送者**的轻量 relation 构建，将结果写入 `results_dict["relation_info"]`，并在群聊回复模板中恢复 `relation_info_block` 占位与传参（当前被注释处取消注释并传 relation_info）。

这样，**读**在回复链统一、群聊私聊都生效；**写**仅在 Summarizer 与 Dream 中发生，与文档中的阶段 4/5/定时任务一致。

### 6.4 关键调用链（关系相关）

- **写关系（自动）**：`ChatHistorySummarizer._store_to_database` 成功 → 若 `enable_relationship` → 对 `participants` 中已知用户调用 `store_person_memory_from_answer(person_name, summary_or_key_point, chat_id)`。
- **写关系（Dream 工具）**：Dream 工具 `store_person_relation`（或同名）→ `store_person_memory_from_answer(...)`；工具在 **dream_agent** 的 `init_dream_tools(chat_id)` 中注册。
- **读关系（轻量）**：`group_generator / private_generator` 在构建 prompt 前 → 轻量方法取当前发送者的 relation 字符串 → 传入 `relation_info_block`。

按上述在仓库中搜索对应符号即可对照实现与文档一致。
