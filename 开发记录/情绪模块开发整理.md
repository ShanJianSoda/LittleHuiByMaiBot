# 情绪模块开发整理

本文档从 `开发记录/dev.md` 中整理出情绪系统相关需求与规划，便于与 `src/mood/` 下实现与文档对照。

---

## 一、需求来源与目标

- **参考**：index-TTS 的情绪维度——8 浮点数列表，顺序为  
  `[快乐, 愤怒, 悲伤, 害怕, 厌恶, 忧郁, 惊讶, 平静]`  
  即 `[happy, angry, sad, afraid, disgusted, melancholic, surprised, calm]`。
- **理解过程**：
  - 借鉴 TTS 的八维度，同时要求：
    - **随机初始化**（有偏好）
    - **连续性**：间隔 n 秒更新，占比来自「聊天内容、自身状态、外界（留拓展）」
    - **函数约束**：防止情绪跳跃
  - 迭代考虑：当前信息、相关记忆（类似的事、相关的人）、先前的情绪。
  - 初步流程：**信息 → 情绪变化 → 影响记忆检索 → 影响回复**。

---

## 二、现有 mood_manager 生命周期（不变部分）

1. **初始化**：`await mood_manager.start()` 启动情绪回归后台任务；`ChatMood` 懒加载。
2. **情绪更新（写入）**  
   `message_handler._preprocess_message()` → `chat_mood.update_mood_by_message()`  
   - 按 interest_rate 与时间概率决定是否更新  
   - 调用 LLM 生成新情绪状态  
   - 更新 `mood_state`、`last_change_time`
3. **情绪使用（读取）**  
   - `plan_filter._build_prompt()`：影响动作决策  
   - `default_generator.build_prompt_reply_context()` / `build_prompt_rewrite_context()`：影响回复生成与重写  
   - `proactive_thinking_executor.gather_context()`：影响主动思考  
   - `planner.get_mood_stats()`：情绪统计与查询
4. **后台维护**  
   `MoodRegressionTask.run()` 每 30 秒执行，对超过 3 分钟未更新的聊天流调用 `chat_mood.regress_mood()`，使情绪回归平静。

## 五、与 VAD 原数据的关系

- **路径**：`data/emotion/`
  - `Chinese-Simplified-NRC-VAD-Lexicon.txt`：中英对照 NRC-VAD，列：English Word, Valence, Arousal, Dominance, Chinese-Simplified Word
  - `nrc_vad_internal.json`：供运行时加载的内部格式 `{ "word": { "v", "a", "d" } }`，值域建议 [-1,1]；需从上述 txt 转换，中文场景建议以**中文词**为 key 或中英双索引。
- **用途**：词典估计（mood_estimator）、可选地在概括器/做梦模块中复用（规划 1.2）。

## 六、小结

- **TTS 对接**：对外可保留 8 维接口（或从 VAD 映射到 8 维），与 index-TTS 对齐。  
- **内部状态**：采用 VAD（或 V/A/D）连续向量，便于连续性、衰减、记忆权重与检索。  
- **实现策略**：不改 `mood_manager` 核心逻辑，在其外增加 VAD/动力学/环境适配层（见 `README_框架.md`），再按上述 7 条逐步落地。

### VAD 初始化与动态过程（use_vad_path = true 时）

- **设计原则**：AI-bot 一致性。**全 bot 单一 VAD**，所有聊天流共享同一情绪状态（与默认「感觉很平静」一致）。
- **初始化**：无集中启动。全 bot 唯一 `MoodDynamics` 在首次 `compute_delta_with_framework` 或 `get_global_dynamics` 时懒加载，`state = [0, 0, 0]`。
- **更新**：任意 chat 消息命中概率后，`compute_delta_with_framework(chat_id, ...)` 用该 chat 的环境因子调制 delta，更新**全局** VAD → `mood_manager.mood.mood_state = vad_to_bucket(...)`（全 bot 单一 ChatMood）。
- **回归**：`MoodRegressionTask` 每周期对全局 VAD 仅执行一次 `tick_only()`，再写回 `mood_manager.mood.mood_state`；`record_emotion_change("global", ...)`。
- **配置**：`config.mood.use_vad_path`；详见 `src/mood/emotion_engine.py` 模块文档。

### 并发与异步（已做防护）

- **运行模型**：主流程为 asyncio 单线程，无多线程共享 mood 状态；多 chat 消息可能并发 `update_mood_by_message`，且与定时任务 `MoodRegressionTask` 交错。
- **已做防护**：
  - **ChatMood._initialize**：使用 `asyncio.Lock`（`_init_lock`）保证只初始化一次，避免并发下重复请求 chat_manager、重复创建 mood_model。
  - **mood 更新/回归串行化**：`MoodManager._mood_lock` 保护「更新情绪」与「回归情绪」的整段逻辑。`update_mood_by_message` 在 `_initialize` 后持锁执行（含 VAD 或 LLM 路径）；`regress_mood` 整段持锁；VAD 路径下 `MoodRegressionTask.run` 仅在写回 `mood_state` 的短临界区持锁，非 VAD 路径通过调用 `regress_mood()` 间接持锁，避免死锁。
- **未加锁但可接受**：`insomnia_chats`、`mood_api._unlock_tasks`、`get_complex_env_adapter` 的 `_adapters` 仅在 asyncio 单线程内读写，当前无锁；`get_global_dynamics()` 懒加载在单线程下只执行一次。
- **可选优化**：`record_emotion_change` 为同步写库，在异步路径中会阻塞事件循环，若写库变慢可改为 `run_in_executor` 或异步存储。

## 八、消息模型与存储（与情绪/VAD 相关）

- **MessageBase**（maim_message）：上游协议层消息基类，含 `message_info`、`message_segment`、`raw_message` 等。
- **Message / MessageRecv**（src/chat/message_receive/message.py）：继承 MessageBase，增加 `chat_stream`、`processed_plain_text`、`interest_value` 等，表示「接收到的、尚未或正在入库」的一条消息。
- **MessageSending**：表示「要发送」的消息，也会经 `MessageStorage.store_message` 写入 DB（display_message、无 interest_value）。
- **Messages**（database_model）：Peewee 表模型，对应 DB 表 `messages`。字段含 `processed_plain_text`、`interest_value`、**emotion_v / emotion_a / emotion_d**（消息级 VAD，入库时由 storage 计算）。
- **DatabaseMessages**（database_data_model）：内存中的数据模型，用于从 DB 查出的消息或跨模块传递；由 `message_repository` 等通过 `DatabaseMessages(**model.__data__)` 从 Messages 构造，含 `emotion_v/a/d`。
- **VAD 事实层**：在 `MessageStorage.store_message` 中，对每条入库消息的 `processed_plain_text` 调用 `estimate_from_lexicon` 得到 (v,a,d)，写入 `Messages.emotion_v/a/d`。情绪更新（VAD 路径）时若 message 已带 `emotion_v/a/d` 则用 `compute_delta_with_framework(..., message_vad=(v,a,d))`，否则用正文现场估计。

## 九、本次已完成（近期改动）

- **概括器 + 关系与 category**
  - 话题分析 prompt 增加 **category** 字段（可选分类：工作、生活、偏好、情感、娱乐、学习、其他）；`TopicCacheItem` 增加 `category`，持久化与映射时同步。
  - `_store_to_database` 成功后，若 `enable_relationship`，对参与者调用 `store_person_memory_from_answer(person_name, memory_content, chat_id, category=item.category)`。
  - **store_person_memory_from_answer** 增加可选参数 `category`，非法或未传则用「其他」。
  - **Dream**：新增工具 `store_person_relation(person_name, memory_content, category)`，内部调用 `store_person_memory_from_answer`；dream 提示词中已说明该工具。
- **消息级 VAD（事实层）**
  - **Messages** 表与 **DatabaseMessages** 增加 `emotion_v`、`emotion_a`、`emotion_d`（FloatField/null）。
  - **MessageStorage.store_message** 中在入库前调用 `_compute_message_vad(filtered_processed_plain_text)`，将结果写入 `Messages.emotion_v/a/d`。heartflow_message_processor 处仅保留注释说明。
  - **emotion_engine.compute_delta_with_framework** 增加可选参数 `message_vad: Optional[Tuple[float,float,float]]`；若传入则跳过 `estimate_from_lexicon`，用该值作 delta 基底再乘环境因子。
  - **mood_manager**（VAD 路径）：若 message 已带 `emotion_v/a/d` 则传 `message_vad`，否则用正文现场估计。
- **数据库**：新字段依赖现有 `initialize_database()` 的缺列自动 ADD COLUMN，无需单独迁移脚本。
