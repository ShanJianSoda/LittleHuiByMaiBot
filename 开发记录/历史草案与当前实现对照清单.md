# 历史草案与当前实现对照清单

这份文档用于整理 `开发记录/` 根目录下若干历史设计草案，与当前项目实际实现之间的关系。

目标不是“复活旧草案”，而是：

- 提炼仍然有效的设计思想；
- 判断哪些内容已经被当前实现吸收；
- 判断哪些内容值得后续继续推进；
- 明确哪些方向应视为历史阶段方案，不再继续整合。

当前对照的主要历史文档包括：

- `开发记录/消息处理与回复完整流程.md`
- `开发记录/新心跳系统开发文档.md`
- `开发记录/心跳系统V2开发文档草案.md`
- `开发记录/notice_and_heartbeat_design.md`

当前主要参考实现包括：

- `src/chat/heartbeat_v2/state_fabric.py`
- `src/chat/heartbeat_v2/system.py`
- `src/chat/heartbeat_v2/planner.py`
- `src/chat/heartbeat_v2/executor.py`
- `src/chat/heartbeat_v2/router.py`
- `src/chat/heartbeat_v2/skill_orchestrator.py`
- `src/chat/heartbeat_v2/reflection.py`
- `src/chat/heartbeat_v2/experience_store.py`

## 总结判断

这些历史草案真正有价值的共识，不是某一版目录结构或某一段旧实现，而是下面这条主线：

- AI 不应只是“收到消息就回复”。
- AI 应该成为一个持续观察环境、调度能力、沉淀经验、逐步修正行为的系统。

当前项目的 `heartbeat_v2 + state_fabric + planner + executor + skill_orchestrator + reflection + experience_store`，已经明显走在这条路上。

因此，后续工作应当是：

- 继续吸收历史草案中的高价值抽象；
- 避免回退到旧版局部实现；
- 不急着引入过重、过远期、低收益的设计。

## 待吸收

这些设计方向是正确的，但当前实现只吸收了部分，建议后续分阶段推进。

| 历史设计点 | 来源文档 | 当前状态 | 建议 |
|---|---|---|---|
| 被动回复主链与 `heartbeat_v2` 桥接 | `消息处理与回复完整流程.md` | 尚未真正桥接 | 目前 `heartbeat_v2.reply` 仍是直接发送短文本，未来应接入更成熟的回复生成链。 |
| LLM planner 替代规则 planner | `新心跳系统开发文档.md` | 当前仍以规则 planner 为主 | 待 state summary 更稳定后再考虑接入。 |
| `receipt -> followup intent` 自动回流 | `心跳系统V2开发文档草案.md` | 还未形成自动链式回流 | 适合用于 `tool_call -> reply`、`memory -> reply`。 |
| mood 对 planner 的软调制 | `开发记录/mood/*` | 已有 mood state，但未深度影响策略选择 | 建议先做软权重，不做重算法。 |
| 群聊/私聊/notice/多模态分场景策略 | 多份草案延伸 | 当前策略粒度仍偏统一 | 适合进一步做成分场景的 `skill_combo` 和 `selection_mode` 学习。 |
| 关系记忆、话题记忆对主动行为的影响 | `消息处理与回复完整流程.md` 相关内容 | 记忆系统已存在，但对主动规划影响有限 | 后续可增强 planner 对人物关系和长期偏好的利用。 |
| tool_call 之后自动判断是否回复 | 多份草案隐含需求 | 当前 skill 执行与 reply 仍分离 | 可做成 follow-up intent 生成器。 |
| 行为风险分级与更细策略门控 | 多份草案中的风险/成本/打扰性思路 | 已有初步字段，但仍较简化 | 值得继续完善。 |
| mood/记忆/notice 的联合优先级评估 | 多份草案共同指向 | 目前已有部分字段，但尚未做综合评分增强 | 适合作为 planner 下一阶段升级方向。 |

## 放弃

这些内容不建议继续整合到当前框架中，应视为历史方案或低收益方向。

| 历史设计点 | 来源文档 | 放弃原因 |
|---|---|---|
| 继续沿旧 `heartbeat` 目录扩展 | `notice_and_heartbeat_design.md` 关联旧方案 | 当前主线已经是 `heartbeat_v2`，旧结构不应继续作为主参考。 |
| 立即完全替代旧消息处理/回复主链 | 对 `消息处理与回复完整流程.md` 的激进延伸 | 风险较高，容易导致回复质量退化。 |
| 一步到位做超重 LLM 总规划层 | `新心跳系统开发文档.md` 的理想化部分 | 当前更需要稳住闭环，不适合先引入过重的规划系统。 |
| 过早做强化学习或在线参数训练 | 一些未来设想 | 当前项目阶段主要收益仍来自外部记忆与策略学习。 |
| 复杂多模态融合算法先行 | 多模态相关设想 | 当前统一 observation 已足够，重融合 ROI 不高。 |
| 过度平台化、过度协议化设计 | 新心跳草案里的泛化设计 | 会拖慢当前项目的工程落地。 |
| 以“心跳直接生成自然语言独白”作为主路线 | 部分早期设想 | 成本高、可控性差，当前不如继续强化 action 闭环。 |

## 过时或需要特别注意的点

这些内容不是简单的“好/坏”，而是需要明确知道它们与现状的关系。

### 1. `消息处理与回复完整流程.md` 不是过时文档

它的价值在于：

- 描述了当前真实主链路；
- 解释了旧消息处理和回复系统今天仍然承担的职责；
- 帮助我们避免在 `heartbeat_v2` 尚未完全成熟时，贸然拆掉旧主链。

因此，这份文档更像“现状系统边界说明书”，而不是未来架构蓝图。

### 2. `notice_and_heartbeat_design.md` 的思想仍有价值，但实现路径已过时

值得保留的是：

- notice 作为高优先级信号；
- notice 进入状态层而不是当作普通消息文本处理；
- poke、输入状态、撤回等行为信号应参与心跳决策。

不应照搬的是：

- 旧版 `heartbeat` 目录下的具体实现结构；
- 为旧工程路径设计的细节规则。

### 3. `心跳系统V2开发文档草案.md` 的抽象仍然有效

这里最值得保留的是：

- `state -> intent -> plan -> receipt -> reflection` 的抽象；
- 记忆、工具、reply、no_op 等 action 一等化；
- 执行结果回流学习的方向。

这里已经部分过时的是：

- memory state 仍只是占位的描述；
- router 仅支持 reply/no_op 的描述；
- tool_call 尚未开展的描述。

这些在当前代码里已经被进一步实现。

## 当前建议

如果后续继续演进，优先级建议如下：

1. 继续强化 `heartbeat_v2` 作为全局编排层。
2. 做好与旧回复主链的桥接，而不是替代。
3. 让记忆、skill、selection_mode 学习继续深入。
4. 逐步引入分场景策略，而不是过早引入重型模型规划或参数训练。

## 一句话结论

历史草案最值得继承的，不是某一份旧文档的具体实现方式，而是它们共同指向的这件事：

> 让 AI 从“收到消息就回复”升级成“持续观察、调度能力、沉淀经验、逐步修正行为”的系统。

当前项目已经在这条路上，后续应继续吸收这些高价值抽象，而不是回退到旧实现或跳向过重的未来主义方案。
