# 内存占用与优化说明

本文档记录项目中可能导致内存持续增长（超过 1G）的排查结果与已做优化。

## 已发现并修复的问题

### 1. 心流聊天实例无限累积（主要来源）

- **位置**: `src/chat/heart_flow/heartflow.py`
- **原因**: `heartflow_chat_list` 只增不减，每有一个新聊天触达就新建并永久保留 `HeartFChatting` / `BrainChatting` 实例，每个实例包含循环任务、概括器、表达学习器等，长时间运行后内存持续上升。
- **修复**:
  - 引入 `MAX_HEARTFLOW_CHATS = 80`，缓存数量超过时按 **LRU** 淘汰最久未访问的聊天。
  - 淘汰时调用该实例的 `stop()`（取消主循环、停止概括器），并从 `heartflow_chat_list` 与 `_last_access` 中移除。
  - 同步清理该 `chat_id` 在 `expression_learner_manager`、`frequency_control_manager`、`reflect_tracker_manager` 中的缓存，避免残留引用。

### 2. 单聊/群聊的 history_loop 无限增长

- **位置**: `src/chat/heart_flow/heartFC_chat.py`、`src/chat/brain_chat/brain_chat.py`
- **原因**: 每次思考循环都会 `history_loop.append(cycle_detail)`，列表无上限，单个聊天长期活跃会积累大量 `CycleDetail`（含 loop_plan_info、loop_action_info、timers 等）。
- **修复**: 在 `end_cycle` 中限制长度，仅保留最近 **30** 条（针对「聊天流少但长期存在」场景，减少单聊内常驻内存）。

### 3. 聊天少但长期存在：单聊内话题与消息累积

- **位置**: `src/memory_system/chat_history_summarizer.py`
- **原因**: 只有 3～4 个聊天流且长期不退出时，每个聊天内的 `topic_cache` 可能持续增加话题数，且每个话题的 `messages` 列表（每次检查的合并文本）也会增长。
- **修复**:
  - **话题数上限**: `MAX_TOPIC_CACHE_SIZE = 25`。超过时优先打包并淘汰「最久未更新」（`no_update_checks` 高）的话题，再写入数据库并从缓存移除。
  - **单话题消息条数上限**: `MAX_MESSAGES_PER_TOPIC = 5`。每个话题只保留最近 5 条合并消息文本，多余的丢弃，避免单话题占用过大。

## 其他已确认有上限或可接受的设计

- **plan_log**（`ActionPlanner` / `BrainPlanner`）: 已有 `len > 20` 时 `pop(0)`，有上限。
- **ChatHistorySummarizer.topic_cache**: 除上述上限外，话题在“打包存储”后会 `pop(topic)`，`current_batch` 在触发检查后会清空，有自然收敛。
- **context_smoother.message_timestamps**: 使用 `deque(maxlen=500)`，有上限。
- **anti_crawler.request_times**: 按 IP 的 deque，需注意单 IP 的 deque 若未设置 maxlen 可能增长，但通常有清理逻辑。

### 4. 优化：去掉 get_or_create_stream 的 deepcopy（减少峰值与分配）

- **位置**: `src/chat/message_receive/chat_stream.py`
- **原因**: 每次 `get_or_create_stream` 都对 stream 做 `copy.deepcopy(stream)`，深拷贝会临时拉高内存且加重 GC。
- **修复**: 改为直接更新并返回缓存中的 stream（更新 user_info、group_info、set_context），不再深拷贝，调用方不依赖“独立副本”，从而减少分配与峰值内存。

## 仍可能带来内存压力的点（未改代码，仅说明）

1. **ChatManager.streams / last_messages**  
   - `get_or_create_stream` 会一直往 `streams` 里加；已去掉深拷贝，若群/私聊数量极多，可考虑按 `last_active_time` 淘汰长期未活跃的 stream。

2. **expression_learner_manager.expression_learners**  
   - 现在会随 heartflow 的 LRU 淘汰同步 `pop(chat_id)`，不再单独无限增长。

3. **ChatHistorySummarizer**  
   - 已加 `MAX_TOPIC_CACHE_SIZE`、`MAX_MESSAGES_PER_TOPIC`，长期单聊内话题与消息条数有上限。

## 如何观察内存

- 使用系统任务管理器或 `ps` 观察进程 RSS。
- **内置内存日志**：已加入定时内存监控任务（`src/common/memory_monitor.py`），每约 30 分钟输出一次各组件数量；当 **RSS ≥ 800MB** 时会以 **WARNING** 打出「内存占用偏高」并输出当前统计，便于定位大对象。统计项包括：
  - `RSS`：进程当前常驻内存（MB）
  - `heartflow_chat_count` / `heartflow_history_loop_lens`：心流聊天数、各聊 history_loop 长度
  - `chat_manager_streams_count` / `chat_manager_last_messages_count`：聊天流数、最后消息数
  - `expression_learners_count` / `frequency_control_count`：表达学习器与频率控制实例数
  - `summarizer_topic_cache_by_chat` / `summarizer_topic_cache_total`：各聊话题缓存条数及总和
- 阈值与间隔：在 `main.py` 中通过 `MemoryMonitorTask(threshold_mb=800, run_interval=1800, wait_before_start=120)` 可调（默认 800MB、30 分钟、启动后 2 分钟首次打点）。
- Python 侧可用 `tracemalloc` 或 `memory_profiler` 做更细粒度分析。

## 可调参数

- **心流缓存上限**: `src/chat/heart_flow/heartflow.py` 中的 `MAX_HEARTFLOW_CHATS`（当前 80）。聊天数很少（如 3～4 个）时一般不会触发淘汰；机器内存紧张可适当调小。
- **单聊 history_loop 保留条数**: `heartFC_chat.py` / `brain_chat.py` 的 `end_cycle` 中当前为 **30**。需要更多轮次上下文可改大，内存紧张可改小。
- **单聊话题缓存上限**: `chat_history_summarizer.py` 中 `MAX_TOPIC_CACHE_SIZE`（当前 25）、`MAX_MESSAGES_PER_TOPIC`（当前 5）。话题极多的群可适当调大，内存紧张可调小。
- **内存监控阈值/间隔**: `src/common/memory_monitor.py` 中 `DEFAULT_HIGH_RSS_MB`（默认 800）；`main.py` 中 `MemoryMonitorTask(threshold_mb=..., run_interval=..., wait_before_start=...)`。

## systemd 常见报错与正确写法

- **Unknown key 'StartLimitInterval>'**：多为配置行被截断或换行错误。正确键名为 **`StartLimitIntervalSec`**（单位秒），且整行不要拆成两行，例如：`StartLimitIntervalSec=60`。
- **Unit uses MemoryLimit=; please >**：说明 `MemoryLimit=` 后面没有写值或值不合法。若需要限制进程内存，应写完整，例如：`MemoryLimit=1G`；若不需要限制，删除该行即可。
