# 心跳系统 V2 开发文档草案

> 文档状态：Draft v0.1  
> 目标：将现有 `heart_flow` 升级为「全局心跳中枢 + 意图队列 + 执行回流」架构。  
> 范围：设计与工程落地方案，不受当前 `src/chat/heartbeat/*` 雏形实现约束。

---

## 1. 背景与目标

当前系统的主要问题：

- 决策权分散：`heart_flow`、回复器、插件侧主动行为存在交叉判断。
- 缺少全局仲裁：多 chat、多动作（reply/search/memory/tool）缺乏统一排序与预算控制。
- 多阶段链不足：难以稳定支持「先查再说」「执行后回流再决策」。

V2 目标：

- 心跳系统作为唯一 `Should Act` 决策中枢。
- 所有能力统一抽象为意图和动作（reply/searchWeb/findMemory/toolCall/noOp）。
- 引入意图队列 + 执行回执回流，形成闭环。
- 支持多频心跳与对话接管（handoff）机制，兼顾真实性与响应效率。

---

## 2. 核心设计原则

1. 单一决策源  
   - 是否行动、何时行动、优先级排序只能在 Heartbeat Core 决定。
2. 执行器无主观  
   - 执行器只负责 `How To Act`，不再自行判断是否触发动作。
3. 意图优先于动作  
   - 队列中存的是 Intent，执行前再展开 Plan，避免过早耦合细节。
4. 回执驱动演进  
   - 每次执行都要有 Receipt，Receipt 可生成后续 Intent（多阶段链核心）。
5. 主动沉默合法化  
   - `no_op` 是正式动作，不是失败分支。
5. 代码要求
   - 代码符合原项目代码规范，同时有合适的注释，异常处理和日志输出

---

## 3. 总体架构

```text
Heartbeat Core
├─ State Fabric
│  ├─ Mood State
│  ├─ Memory State
│  ├─ Chat/Notice State
│  ├─ Metadata State
│  └─ Deliberation History (最近N次心跳)
│
├─ Planner
│  ├─ Intent Providers
│  ├─ Intent Normalizer
│  ├─ Intent Scorer
│  └─ Policy Gate
│
├─ Intent Queue
│  ├─ ready queue
│  ├─ delayed queue
│  └─ dedup/expire
│
├─ Executor
│  ├─ Intent -> Plan
│  ├─ Action Router
│  └─ Receipt Recorder
│
└─ Feedback Loop
   ├─ Receipt -> State Update
   └─ Receipt -> New Intent (optional)
```

## 4. 核心数据结构（建议）

### 4.1 Intent

```python
@dataclass
class Intent:
    intent_id: str
    source: str                  # mood / memory / notice / scheduler / receipt / external
    type: str                    # engage / explore / retrieve / reflect / handoff / no_op
    target_chat_id: str | None
    target_user_id: str | None
    payload: dict[str, Any]

    priority: float
    urgency: float
    confidence: float
    cost_hint: float
    risk_hint: float

    dedup_key: str | None
    created_at: float
    expire_at: float | None
```

### 4.2 Plan

```python
@dataclass
class Plan:
    plan_id: str
    intent_id: str
    action_type: str             # reply / search_web / find_memory / tool_call / handoff_dialogue / no_op
    action_args: dict[str, Any]
    policy_tags: list[str]
    timeout_s: int
```

### 4.3 PlanGraph（可选，P2 引入）

```python
@dataclass
class PlanNode:
    node_id: str
    action_type: str
    action_args: dict[str, Any]
    depends_on: list[str]

@dataclass
class PlanGraph:
    plan_id: str
    intent_id: str
    nodes: list[PlanNode]
```

### 4.4 ExecutionReceipt

```python
@dataclass
class ExecutionReceipt:
    receipt_id: str
    plan_id: str
    intent_id: str
    action_type: str
    status: Literal["success", "failed", "skipped", "deferred"]
    reason: str | None
    outputs: dict[str, Any]
    cost_actual: float | None
    latency_ms: int
    timestamp: float
```

## 5. 队列与调度策略

### 5.1 队列模型

- `ready_queue`：立即可执行 intent（按 score 排序）。
- `delayed_queue`：受冷却/窗口限制，未来执行。
- `dead_letter`：执行失败且超过重试上限的 intent。

### 5.2 入队规则

- 去重：`dedup_key + time_window`。
- 过期：`expire_at` 到期即丢弃。
- 合并：同一目标同类低价值 intent 可合并（例如重复的轻度闲聊意图）。

### 5.3 出队规则

- 先过 Policy Gate（预算、冷却、时段、安全）。
- 再执行资源检查（chat/memory/tool 并发槽）。
- 若不可执行，转 `delayed_queue` 或标记 `skipped`。

### 5.4 优先级评分（建议）

`score = w1*priority + w2*urgency + w3*confidence - w4*cost_hint - w5*risk_hint - w6*interruptiveness`

补充因子：

- `recent_action_penalty`：连续主动行为惩罚。
- `target_fatigue_penalty`：同一对象短期触达惩罚。
- `timing_bonus`：窗口时机加成（如刚提及、刚触发 notice）。

---

## 6. 多频心跳职责

- `fast loop`（秒级）  
  只做轻量事件检查与高优先意图插队，不做重推理。

- `normal loop`（10-60秒）  
  主规划循环：collect -> score -> queue -> execute（受预算控制）。

- `slow loop`（分钟级）  
  全局清理、统计归档、策略参数微调、历史截断。

---

## 7. 标准时序（4条）

### 7.1 初始化时序

```text
Main -> HeartbeatSystem.start()
HeartbeatSystem -> StateFabric.bootstrap()
HeartbeatSystem -> IntentQueue.bootstrap()
HeartbeatSystem -> start fast/normal/slow loops
```

### 7.2 空闲触发规划时序

```text
normal_tick ->
  if queue.empty and system.awake:
    Planner.collect_inputs(mood/memory/metadata/historyN)
    Planner.generate_intents()
    IntentQueue.enqueue(intents)
```

### 7.3 多阶段行为链时序（先查再发）

```text
Intent(explore_topic) ->
Executor.expand_to_plan_graph ->
  node1: search_web
  node2: summarize (depends node1)
  node3: find_memory/update_memory (depends node2)
  node4: reply or handoff_dialogue (depends node2/node3)
each node -> receipt -> feedback loop
```

### 7.4 对话接管时序（handoff）

```text
Heartbeat decides handoff_dialogue ->
DialogueAdapter takes lease(chat_id, ttl) ->
Heartbeat enters suspended_by_dialogue (normal降频, fast保活) ->
DialogueAdapter emits receipt(done/timeout/fail) ->
Heartbeat exits suspended state
```

## 11. 风险与约束

- LLM 规划成本上升风险：需限制 normal tick 的重推理频率。
- 迁移期双系统并存风险：必须有单一主决策开关，避免双发言。
- 插件直接发消息绕过风险：新增规范，插件主动行为必须走 Intent 提交。

## 14. 附录A：模块迁移表（旧定时任务 -> 新 IntentProvider/ActionAdapter）

## 15. 附录B：3-lane 队列调度规则

### 15.1 三车道定义

- `urgent lane`（高优先）  
  目标：秒级响应用户高时效事件。  
  典型 Intent：`urgent_reply`, `notice_response`, `safety_interrupt`

- `normal lane`（中优先）  
  目标：常规对话与工具/记忆协同行为。  
  典型 Intent：`reply`, `search_web`, `find_memory`, `handoff_dialogue`

- `maintenance lane`（低优先）  
  目标：系统维护与长期质量提升。  
  典型 Intent：`summarize_chat`, `dream_maintain`, `expression_check`, `stats_snapshot`

### 15.2 出队配额（建议默认）

- 每个 `normal tick` 的最大执行预算：`max_actions_per_tick = 6`
- 默认 lane 配额：`urgent:normal:maintenance = 3:2:1`
- 若 `urgent lane` 为空，其配额可借给 `normal lane`；`maintenance` 仅在系统负载低时借位。

示例：

- 本轮可执行 6 个动作，且三个 lane 都有任务：  
  执行顺序优先按 lane，再按 lane 内 score：`U,U,U,N,N,M`
- 若 `urgent` 只有 1 个任务：  
  剩余 2 个高优先配额可下放给 normal：`U,N,N,N,N,M`

### 15.3 Lane 内排序规则

lane 内按统一评分排序：

`lane_score = base_score + timing_bonus - fatigue_penalty - budget_penalty`

- `base_score`：由 Planner 给出的优先级/紧急度/置信度
- `timing_bonus`：时效窗口加成（刚被@、刚有notice）
- `fatigue_penalty`：同目标连续触达惩罚
- `budget_penalty`：高成本动作在预算紧张时降权

### 15.4 降级与回退策略

- 预算不足：
  - `urgent` 不降级，保证关键响应。
  - `normal` 优先保留低成本动作（如简短 reply）。
  - `maintenance` 延迟到 `delayed_queue`。
- 执行失败：
  - 可重试动作进入重试队列，带指数退避。
  - 不可重试动作写 `dead_letter` 并产生失败 receipt。
- 队列积压：
  - `maintenance` 自动限流。
  - 同类低价值 intent 自动合并（按 `dedup_key`）。

### 15.5 与多频心跳的对应关系

- `fast loop`：只拉取 `urgent lane`，并且禁止高成本动作。
- `normal loop`：主要消费 `urgent + normal`，按配额允许少量 `maintenance`。
- `slow loop`：优先消费 `maintenance lane`，并执行清理/统计/策略校正。

### 15.6 最小观测指标（落地必备）

- 每 lane 当前长度、入队速率、出队速率、过期丢弃数
- 每 lane 平均等待时长（p50/p95）
- 每 lane 成功率/失败率
- 配额借位次数（urgent->normal, normal->maintenance）
- maintenance 延迟累计时长（防止长期饿死）
