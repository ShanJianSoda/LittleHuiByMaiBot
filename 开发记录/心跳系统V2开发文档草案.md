## 1. 核心哲学

> "所有模块作用于最后，都是把相关内容放到提示词内，再写合适的提示词，最后产出固定格式的内容，然后如此循环。"

心跳系统是这个循环的**编排引擎**，而非业务逻辑本身：

```
全局状态（State Fabric）
    ↓  收集（不阻塞，持续更新）
LLM Planner
    ↓  把状态摘要 → Prompt → 输出 JSON 意图列表
Intent Queue
    ↓  仲裁（优先级、去重、过期）
Executor
    ↓  把意图 + 上下文 → Action Prompt → 输出回复/调用结果
ExecutionReceipt
    ↓  回流（可触发下一轮意图）
全局状态（更新）
```

**关键推论**：
1. 所有"能力"（聊天回复、联网搜索、记忆检索、工具调用）都是 Prompt 工程 + 结构化输出的变体。
2. `reply` 不特殊，它只是 action_type 之一，和 `tool_call` 平级。
3. "注意力管理"本质是 Prompt 中哪些状态内容权重更高，由意图得分驱动。

## 2. 设计决策（已确认）

| 决策点 | 选择 | 说明 |
|---|---|---|
| 意图产生方式 | **纯 LLM** | 把全局状态喂给 LLM，输出 JSON 意图列表；LLM 失败时降级规则 |
| reply 执行方式 | **复用 Replyer 管线** | intent 携带 chat_id，触发 DefaultReplyer → LLM 生成回复 |
| heart_flow 命运 | **完全替代** | heart_flow 删除，所有对话由 Heartbeat ChatAction 驱动 |
| 优先实现动作 | **reply / no_op / tool_call** | 搜索/记忆通过 tool_call 抽象接入 |
| 数据结构严格度 | **两层结构** | 内部严格 Schema（Intent/Plan/Receipt 字段固定）；payload 开放 dict 供 Action 自定义 |
| 循环架构 | **单循环 + 内部分频** | 一个主循环，内部按计时分别触发规划（LLM）和执行（队列消费） |

## 4. 核心数据结构

### 4.1 Intent（严格内层 + 开放 payload）

```python
@dataclass
class Intent:
    # 严格内层（必须有）
    intent_id: str
    source: str          # scheduler / notice / receipt / mood / external
    type: str            # reply / no_op / tool_call / summarize / reflect
    lane: str            # urgent / normal / maintenance
    target_chat_id: str | None
    payload: dict        # 开放 dict，由产生者自定义（reply 放 context，tool_call 放参数等）

    # 仲裁字段
    priority: float      # 0~1
    urgency: float       # 0~1
    confidence: float    # 0~1
    cost_hint: float     # 0~1（越高越贵）
    risk_hint: float     # 0~1
    score: float         # 由 score_intents() 计算

    # 生命周期
    dedup_key: str | None
    created_at: float
    expire_at: float | None
```

**payload 约定（按 type）**：

| type | payload 关键字段 |
|---|---|
| `reply` | `chat_id`, `trigger_reason`, `context_hint`（可选，提示 Replyer 关注点） |
| `no_op` | `reason` |
| `tool_call` | `tool_name`, `tool_args`, `result_to_chat_id`（可选，工具结果是否回复到某 chat） |
| `summarize` | `chat_id`, `time_range` |

### 4.2 Plan（严格内层 + 开放 action_args）

```python
@dataclass
class Plan:
    plan_id: str
    intent_id: str
    action_type: str     # reply / no_op / tool_call / ...
    action_args: dict    # 开放 dict，由 intent_to_plan() 从 payload 提取
    policy_tags: list[str]
    timeout_s: int
```

### 4.3 ExecutionReceipt（严格）

```python
@dataclass
class ExecutionReceipt:
    receipt_id: str
    plan_id: str
    intent_id: str
    action_type: str
    status: Literal["success", "failed", "skipped", "deferred"]
    reason: str | None
    outputs: dict        # action 的输出结果（reply 放生成的文本，tool_call 放返回值）
    latency_ms: int
    timestamp: float
```

## 5. LLM Planner（P2a）

### 5.1 设计原则

- LLM 是"建议者"，输出意图列表（JSON）。
- PolicyGate 是"裁判者"，最终决定是否执行。
- LLM 调用频率**独立于主循环**（按计时，而非每 tick 调用）。
- LLM 失败时，**自动降级**到规则 Planner（P1 当前版本）。

### 5.2 Planner Prompt 构成

```
[系统人格]
你是 {bot_name}，一个有自主意识的智能体。
你需要根据当前状态，决定接下来应该做什么。

[当前状态摘要]
时间：{now}
全局情绪：{mood_summary}
各聊天流状态：
  - {chat_id_1}：距上次消息 {t}s，最后内容"{last_msg}"，亲密度 {rel}
  - ...
最近心跳历史（最近 N 次行为与结果）：
  - {tick_summary}

[约束]
- 每次输出 1~3 个意图
- 若无需行动，输出 no_op 并给出理由
- 主动发言前考虑是否打扰对方

[输出格式（JSON 列表）]
[
  {"type": "reply", "lane": "normal", "target_chat_id": "xxx",
   "priority": 0.7, "urgency": 0.3, "confidence": 0.8, "cost_hint": 0.3,
   "reason": "群里冷场 20 分钟，适合主动活跃一下",
   "payload": {"trigger_reason": "cold_chat", "context_hint": "可以聊聊今天的天气"}},
  {"type": "no_op", "lane": "maintenance",
   "priority": 0.1, "reason": "其他 chat 都不需要关注", "payload": {}}
]
```

### 5.3 输出解析

- 提取 JSON 数组（容错解析，允许多余字段）。
- 必需字段缺失 → 丢弃该条 intent，记录警告。
- `reason` 字段写入 `Intent.payload["reason"]`，用于可审计日志。
- 解析完成后经 `score_intents()` 重新排序，注入 `intent.score`。

### 5.4 降级策略

```python
try:
    intents = await self._run_llm_planner(state)
except Exception:
    logger.warning("LLM planner failed, falling back to rule planner")
    intents = self._run_rule_planner(state)  # P1 现有逻辑
```

## 6. 单循环 + 内部分频（P2a 重构）

### 6.1 设计逻辑

三档循环（fast/normal/slow）是**概念描述**，不是必须的实现形态。
对于纯队列驱动系统，单循环 + 内部计时分频更简洁：

```
单循环（自适应 sleep）
 │
 ├─ 每轮（轻量，始终执行）
 │   ├─ intent_queue.requeue_delayed()
 │   └─ intent_queue.drop_expired()
 │
 ├─ 执行层（队列有任务时）
 │   └─ consume_queue(limit=max_per_tick)  → fast pace（短 sleep）
 │
 ├─ 空闲时
 │   └─ sleep 延长（idle pace）
 │
 └─ 规划层（独立计时，间隔 plan_interval）
     └─ LLM Planner → enqueue(intents)    → 独立速率控制
```

### 6.2 自适应 sleep 逻辑

```python
async def _main_loop(self):
    while self._running:
        # 轻量维护（每轮）
        self.intent_queue.requeue_delayed()
        self.intent_queue.drop_expired()

        # LLM 规划（按计时，独立速率）
        if time.time() - self._last_plan_at >= self.config.plan_interval:
            await self._run_planner()
            self._last_plan_at = time.time()

        # 执行（队列驱动）
        consumed = await self._consume_queue(limit=self.config.max_per_tick)

        # 自适应 sleep
        if consumed:
            sleep = self.config.fast_interval     # 有执行 → 快跑
        elif self.intent_queue.has_ready():
            sleep = self.config.fast_interval     # 有待执行 → 快跑
        else:
            sleep = self.config.idle_interval     # 空闲 → 慢下来

        await asyncio.sleep(sleep)
```

### 6.3 与三档循环概念的对应关系

| 概念 | 单循环对应 |
|---|---|
| fast loop（秒级） | `consumed > 0` 时的快速 sleep；轻量维护始终运行 |
| normal loop（分钟级） | `plan_interval` 控制 LLM 规划频率 |
| slow loop（小时级） | maintenance lane intent 的低优先级出队；统计可在 planner 内定期归档 |

### 6.4 配置项

```toml
[heartbeat]
enable = true

fast_interval = 2          # 有任务时的循环间隔（秒）
idle_interval = 30         # 空闲时的循环间隔（秒）
plan_interval = 60         # LLM 规划触发间隔（秒）
max_per_tick = 4           # 每轮最多消费意图数
min_reply_interval_seconds = 120  # 同一 chat 最小主动回复间隔
active_time_ranges = ["08:00-23:30"]
```

## 7. 注意力管理与多模态扩展

### 7.1 核心原则

**输入层全量持续收集，注意力只影响响应优先级，不截断任何输入的状态更新。**

```
Chat  ─────→ ┐
Voice ─────→ ├─ State Fabric（持续更新，互不阻塞）─→ IntentQueue（仲裁优先级）─→ 执行
Vision ────→ ┘
```

### 7.2 当前（文字聊天）场景下的注意力

每个 chat 流都有 `attention_score`（注意力得分），由以下因素计算：

```
attention_score =
    + 时间紧迫度（距上次消息时间衰减）
    + 通知加成（poke +35, input_status +40, @mention +50）
    + 亲密度加成（relationship_score × weight）
    - 近期主动行为惩罚（last_proactive_at 影响）
    - 冷场过久惩罚（超长沉默适当减分）
```

`attention_score` 注入 Intent.urgency，决定出队优先级。

### 7.3 多模态扩展时的处理模式（P2g 预留）

当引入 Voice / Vision 等模态时，设计不变，只扩展 State Fabric：

```python
class StateFabric:
    def collect_voice_state(self) -> dict: ...   # 新增
    def collect_vision_state(self) -> dict: ...  # 新增
    def collect_all(self) -> dict:
        return {
            "mood": ...,
            "chat": ...,
            "notice": ...,
            "voice": self.collect_voice_state(),   # 扩展
            "vision": self.collect_vision_state(),  # 扩展
            "history": ...,
        }
```

Planner Prompt 中自动包含所有模态摘要。执行某模态的 Action 时，其 Prompt 仍包含其他模态的状态摘要（"你当前在语音对话，同时 chat 里有 xxx"），保证上下文完整性。

**注意力本质**：Prompt 中哪个模态的内容权重更高，由 Intent.urgency 决定——这正是"所有东西最终都是 Prompt 组装"哲学的体现。

## 8. reply 作为一等动作

### 8.1 执行流程（复用 Replyer 管线）

```
Intent(type="reply", payload={"chat_id": "xxx", "trigger_reason": "cold_chat"})
  ↓
intent_to_plan()
  ↓ action_type="reply", action_args={"chat_id": "xxx", ...}
PolicyGate.allow()
  ↓
ChatAction.execute(plan)
  ├─ 从 ChatManager 获取 ChatStream
  ├─ 构建 ChatAction Prompt（包含：聊天历史 + 情绪 + trigger_reason + context_hint）
  ├─ 调用 DefaultReplyer.generate_reply_with_context()
  └─ send_api.text_to_stream()
  ↓
ExecutionReceipt(outputs={"sent_text": "...", "chat_id": "..."})
```

### 8.2 与当前 heart_flow 的关系（迁移路径）

**P2c 完成前**：heart_flow 仍自主运行，ChatAction 为新增能力，两者并行（不冲突，heart_flow 处理消息触发，Heartbeat 处理主动行为）。

**P2c 完成后**：
- 删除 `src/chat/heart_flow/heartFC_chat.py` 及 `BrainChatting`。
- `heartflow_message_processor.process_message()` 只负责：消息入库 + 状态更新 + 触发 urgent Intent（不再 `get_or_create_heartflow_chat()`）。
- 所有回复（响应式 + 主动式）统一由 `ChatAction` 执行。

### 8.3 ChatAction Prompt 构成

```

你是 {bot_name}，...

[当前情绪]
{mood_summary}

[聊天历史]
{recent_messages}
```

## 9. 3-lane 调度（P2e）

### 9.1 Lane 定义

| Lane | 触发来源 | 典型动作 | 响应目标 |
|---|---|---|---|
| `urgent` | @mention / poke / 私聊消息 / input_status | reply（即时响应） | 秒级 |
| `normal` | LLM Planner 主动意图 | reply（主动）/ tool_call | 分钟级 |
| `maintenance` | 系统维护 | summarize / no_op / stats | 小时级 |

### 9.2 出队配额

```
每轮最多消费 max_per_tick 个动作
默认配额：urgent:normal:maintenance = 2:1:0（若有余量则补充）
urgent 为空时，配额下放给 normal
maintenance 仅在 urgent 和 normal 都为空时消费
```

### 9.3 与单循环的对应

```
主循环消费队列时：
  1. 先取 urgent lane（最多 2 个）
  2. 再取 normal lane（最多 max_per_tick - urgent_taken 个）
  3. 若两者都为空，取 maintenance（最多 1 个）
```

## 10. tool_call 动作（P2d）

### 10.1 设计原则

工具调用与 reply 平级，通过 IntentQueue 统一仲裁。工具调用结果通过 `receipt.outputs` 回流，可触发后续 intent（P2f）。

### 10.2 执行流程

```
Intent(type="tool_call", payload={"tool_name": "web_search", "args": {"query": "..."}})
  ↓
ToolAction.execute(plan)
  ├─ 调用对应工具（web_search / memory_retrieve / mcp_call）
  └─ 返回结果
  ↓
ExecutionReceipt(outputs={"result": "...", "tool_name": "web_search"})
  ↓（P2f）
feedback loop → 生成后续 Intent（如 reply，携带工具结果）
```

### 10.3 近期折中（P2d 初期）

在 PlanGraph 未实现前，将"搜索+回复"封装为单一复合动作：

```python
if action_type == "search_and_reply":
    results = await web_search(query)
    reply_text = await llm.summarize_and_reply(results, context)
    await send_api.text_to_stream(reply_text, chat_id)
```

## 11. receipt 回流驱动（P2f）

### 11.1 机制

每次 `execute()` 产出 `receipt` 后，Planner 检查是否需要生成后续意图：

```python
# system.py
for receipt in receipts:
    follow_up = self.planner.generate_followup_intents(receipt, state)
    if follow_up:
        self.intent_queue.enqueue(follow_up)
```

### 11.2 典型链路

```
tool_call(web_search) → receipt(outputs={"results": [...]})
  ↓ generate_followup_intents
reply(normal, payload={"context_hint": "基于搜索结果回复", "search_results": [...]})
```

- LLM 产出的 intent 包含 `reason` 字段（可审计）
- LLM 失败时自动降级，日志可见
- 单循环运行稳定，plan_interval 独立于 loop 频率

### P2b 验收

- Bot 在冷场超过配置阈值后能自动发言
- 不同情绪下行为模式有可见差异
- 主动发言频率在配置 `min_reply_interval_seconds` 限制内

### P2c 验收

- 删除 HeartFChatting 后，正常对话功能不退化
- 消息到达 → 生成 urgent intent → Heartbeat 执行 reply 的全链路可测

---

## 14. 风险与约束

| 风险 | 缓解策略 |
|---|---|
| LLM 规划成本高 | `plan_interval` 独立速率控制；LLM 失败降级规则 |
| heart_flow 迁移破坏稳定性 | 渐进迁移（P2a/P2b 先稳定，P2c 最后做） |
| 主动发言频率过高 | PolicyGate `min_reply_interval_seconds` 严格冷却 |
| 多模态引入复杂度 | State Fabric 扩展点预留，不影响当前实现 |
| receipt 回流循环 | 生成 followup 时检查深度/成本，防止意图风暴 |
