# ikaros 心跳系统开发文档（全局自主规划中枢版）

> 适用定位：**跨项目可复用**的智能体“全局规划系统”设计文档。  
> 设计目标：真实、自主、可扩展、工程可落地。  
> 关键原则：聊天只是行动之一，心跳系统负责统一思考、决策、调度与执行编排。

---

## 1. 设计哲学

心跳系统不是“聊天触发器”，而是智能体的**持续认知与行动编排内核**。

它应具备以下特征：

1. **全局性（Global）**  
   从全局状态做决策：聊天流、通知、任务、工具资源、记忆状态、外部事件、风险约束。

2. **自主性（Autonomous）**  
   不是被动响应消息，而是主动形成“下一步想做什么”。

3. **真实性（Human-like Rhythm）**  
   行为节律自然，不刷屏、不机械；支持注意力切换、延迟响应、反思修正。

4. **可扩展性（Extensible by Design）**  
   任何“意图来源”和“执行能力”都可插拔接入：聊天、联网搜索、MCP 工具调用、记忆检索、计划任务、外部 API。

5. **可治理性（Governable）**  
   有预算、有冷却、有优先级、有安全策略、有可观测性。

---

## 2. 目标边界

### 2.1 目标

- 统一接入多源意图，进行全局仲裁。
- 在不同行动之间做资源分配（聊天、搜索、工具调用、计划执行）。
- 基于上下文与长期记忆，形成持续决策闭环。
- 通过多层心跳节奏实现“紧急响应 + 常规规划 + 慢速反思”。

### 2.2 非目标

- 不限定某个具体业务项目的数据结构。
- 不绑定单一框架或单一模型供应商。
- 不将“主动发言”误当作唯一目标（主动沉默同样可能是更优决策）。

## 4. 核心抽象（推荐）

## 4.1 意图（Intent）

意图是“系统为什么要做某事”的标准化表达。

```python
@dataclass
class Intent:
    intent_id: str
    source: str                     # chat / scheduler / memory / external / ...
    category: str                   # converse / search / tool_call / remind / reflect / ...
    target: dict[str, Any]          # 目标对象（用户、会话、任务、资源）
    payload: dict[str, Any]         # 上下文附加信息

    priority: float                 # 来源优先级
    confidence: float               # 置信度
    utility_hint: float             # 来源估计收益
    risk_hint: float                # 来源估计风险
    cost_hint: float                # 来源估计成本（token/time/tool quota）

    created_at: float
    expire_at: float | None
    dedup_key: str | None = None
```

## 4.2 计划（Plan）

计划是“系统具体准备做什么”的结构化结果。

```python
@dataclass
class Plan:
    plan_id: str
    intent_id: str
    action_type: str                # chat_reply / web_search / mcp_call / memory_retrieve / ...
    action_args: dict[str, Any]

    expected_utility: float
    expected_cost: float
    expected_risk: float

    policy_tags: list[str]
    timeout_s: int
```

## 4.3 执行回执（ExecutionReceipt）

```python
@dataclass
class ExecutionReceipt:
    plan_id: str
    status: Literal["success", "skipped", "failed", "deferred"]
    reason: str | None
    outputs: dict[str, Any]
    latency_ms: int
    cost_actual: float | None
    timestamp: float
```

## 5. 可插拔机制：Provider / Policy / Action

## 5.1 Intent Provider（意图提供器）

```python
class IntentProvider(Protocol):
    name: str
    async def collect(self, now_ts: float) -> list[Intent]: ...
```

可接入来源：
- 聊天事件（冷场、未回复、对话中断）
- 外部通知（系统告警、订阅变更）
- 记忆触发（约定到期、纪念日）
- 任务系统（计划执行点）
- 工具反馈（搜索结果待总结）

## 5.2 Policy Gate（策略闸门）

```python
class PolicyGate(Protocol):
    name: str
    async def allow(self, plan: Plan, state: "GlobalState") -> tuple[bool, str | None]: ...
```

示例策略：
- 全局速率限制
- 单目标冷却
- 安全/合规校验
- 成本预算限制
- 场景禁用时段

## 5.3 Action Adapter（行动适配器）

```python
class ActionAdapter(Protocol):
    action_type: str
    async def execute(self, plan: Plan) -> ExecutionReceipt: ...
```

聊天只是其中一种 `action_type`；系统可统一调度 `web_search`、`mcp_call`、`memory_update` 等行动。

## 6. 决策模型：从“能做”到“该做”

建议将决策分为两步：

1. **Intent -> Candidate Plans**（生成候选计划）
2. **Plan Ranking + Policy Gating**（排序并过闸）

## 6.1 统一评分函数（可替换）

`plan_score = U - C - R + T`

- `U`：预期收益（价值）
- `C`：预期成本（时间、token、工具额度）
- `R`：风险惩罚（安全/打扰/不确定性）
- `T`：时机加成（例如紧急性、窗口期）

可展开为：

`plan_score = w1*utility + w2*urgency + w3*relationship - w4*cost - w5*risk - w6*interruptiveness`

## 6.2 “主动沉默”作为显式动作

必须允许 `no_op` 成为合法高分计划：
- 当前动作收益低于阈值。
- 风险/打扰大于收益。
- 全局预算已紧张。

## 7. 多频心跳（为什么必须多层）

## 7.1 fast loop（秒级）

用途：
- 处理紧急/强时效意图。
- 健康探测与轻量状态校验。

约束：
- 不做重模型推理。
- 不执行高成本工具链。

## 7.2 normal loop（10~60秒）

用途：
- 收集意图、生成计划、排序仲裁。
- 执行常规行动（聊天/搜索/工具调用）。

## 7.3 slow loop（分钟级）

用途：
- 全局统计、记忆整理、策略参数漂移校正。
- 清理过期意图、降权陈旧目标、产出自省摘要。

> 三层的意义不是“更复杂”，而是将**反应速度、推理成本、全局稳定性**解耦。

---

## 8. 队列与调度策略（伪队列建议）

## 8.1 双队列

1. `intent_queue`：原始意图（短生命周期，高吞吐）
2. `plan_queue`：候选计划（低吞吐，高价值）

## 8.2 关键机制

- **去重**：`dedup_key + 时间窗口`。
- **过期**：到期即丢弃，避免“迟到的行动”。
- **优先级老化**：低优先级长期得不到执行时缓慢升权（防饿死）。
- **预算感知**：若预算不足，优先保留高价值低成本计划。

## 8.3 并发建议

- 控制并发槽位（如 `max_concurrent_actions`）。
- 工具调用与聊天行动使用独立资源池，避免互相阻塞。

---

## 9. 与现有聊天模块（如 AFC）的关系

本设计可借鉴任何现有聊天主动思考模块，但不依赖其内部实现。

推荐关系：

- 心跳系统：全局仲裁者（是否触发、触发何种行动）。
- 聊天模块（AFC/KFC/其他）：`Chat Action Adapter` 的执行后端（如何说）。

也就是说：
- 可以继续复用现有聊天决策与生成能力；
- 但是否轮到“聊天行动”由全局规划决定，而不是单模块各自抢时机。

## 10. MCP / 工具 / 联网搜索的一等公民化

要实现“真实自主”，工具调用不能是聊天失败后的兜底，而应是一等行动类型。

## 10.1 工具调用触发条件

- 聊天语义存在事实不确定性。
- 用户上下文需要外部信息补全。
- 当前计划收益依赖外部证据。

## 10.2 工具调用后的标准流程

1. 形成 `tool_call` 计划。
2. 执行后写入 `ExecutionReceipt`。
3. 结果进入记忆或状态。
4. 触发后续 `chat_reply` / `summarize` / `schedule_follow_up` 意图。

## 11. 治理与安全（必须内置）

## 11.1 成本治理

- 全局每小时 token/工具预算。
- 单用户/单会话预算上限。
- 预算不足时的降级策略（简短回复 / 延迟执行 / no_op）。

## 11.2 风险治理

- 高风险行动二次校验。
- 外部工具结果可信度标注。
- 可审计日志（谁触发、为何触发、为何被拒）。

## 11.3 体验治理

- 防打扰冷却（target-level + global-level）。
- 夜间/敏感时段策略。
- “连续主动行为上限”防机械刷存在感。

---

## 12. 可观测性（衡量“像真人”）

建议跟踪：

1. **行为质量**
   - 有效行动率（执行后产生正向反馈）
   - 无效行动率（被忽略/中断/撤销）

2. **节律自然度**
   - 主动行为间隔分布
   - 多目标切换频率
   - 连续主动触达长度

3. **资源效率**
   - 单位收益成本（cost per useful action）
   - 工具调用命中率（调用后是否真正提升结果）

4. **安全与稳定**
   - 策略拒绝率
   - 风险拦截率
   - 计划失败重试成功率

## 13. 参考实现骨架（伪代码）

```python
async def normal_heartbeat_tick(state: GlobalState):
    intents = await intent_bus.collect_all()
    intents = dedup_and_expire(intents, state)

    candidate_plans = planner.expand(intents, state)
    ranked = ranker.sort(candidate_plans, state)

    for plan in ranked:
        allowed, reason = await policy_engine.allow(plan, state)
        if not allowed:
            audit.reject(plan, reason)
            continue

        receipt = await action_router.execute(plan)
        state.apply_receipt(receipt)
        audit.record(receipt)

        if should_yield_after_action(receipt, state):
            break
```

## 14. 迭代路线图

### V1：可运行最小闭环
- Intent Provider + Policy Gate + Chat Action Adapter
- fast/normal 两层心跳
- 基础冷却、预算、日志

### V2：全局能力增强
- 引入 tool/search/mcp 行动类型
- slow loop 自省与统计
- 双队列 + 优先级老化

### V3：高级自主
- 动态参数自适应（节律与预算按反馈调优）
- 长周期目标管理（周/月级）
- 多代理协同（可选）

---

## 15. 最终结论

一个真正面向未来的心跳系统应是：

- **全局规划中枢**，而非聊天定时器集合；
- **行动中立框架**，聊天/搜索/工具/MCP 都是可仲裁行动；
- **策略与治理先行**，确保真实感与稳定性并存；
- **可插拔、可观察、可演进**，可迁移到任何项目与业务形态。

这套设计允许系统在不同上下文下做出“更像人”的选择：
> 有时说话，有时查询，有时调用工具，有时什么都不做——但每一次都应有理由。
