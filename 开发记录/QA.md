# question

这个是新系统设计，但是我认为从真实性，以及速度上我还觉得不够好。框架上也总感觉差些意思。 

比如如何流畅的实现如下内容： 心跳系统进行决策： 常驻信息：情绪系统，前n次心跳系统元信息，可选聊天对象元信息（可自主维护） 情景1： 1. 决策：联网搜索感兴趣的 -> 进行保存 2. 决策：想发送到某个聊天对象（或者群聊） -> 执行决策 -> 后续内容由对话模块接管，心跳系统进行休眠（或者说因为对话模块在进行，而导致的延时） 

情景2： 1. 决策：查看某个聊天对象的历史记录（默认最后n条） 2. 决策：进行主动发送消息 -> 后续由对话模块接管 

---

我目前对心跳系统和回复器的定位有点模糊，或者说这两个本来就有相交的地方。

如何进行优化，分析新文档，然后给我建议



# answer

你现在的困惑，本质上不是“心跳写得不够好”，而是**认知调度权到底在谁手里**没有被彻底理清。

先抽离结构。

根据文档中的设计目标，心跳系统被定义为“全局规划中枢”，聊天只是行动之一新心跳系统开发文档。这句话如果贯彻到底，会直接推翻你当前的模糊点。

问题在于：你在实现时，仍然在把“聊天模块”当成一个半独立智能体，而不是被调度的执行器。

这会导致两个系统在“什么时候思考、什么时候发言、什么时候调用工具”上发生重叠。

下面做一次彻底结构拆分。

------

一、核心架构还缺的东西：运行态边界清晰化

你目前的结构是：

心跳系统 → 决策
 回复器 → 生成内容

但现实上：

回复器内部也在做决策（是否需要搜索、是否延迟、是否主动延伸）

这就是冲突来源。

必须把决策权分层：

第一层：是否行动（Should Act）
 第二层：如何行动（How To Act）

第一层只属于心跳系统。
 第二层只属于具体 Action Adapter。

聊天模块只负责：

- 给定 plan（例如：向 A 发送 X 内容）
- 返回生成结果

聊天模块不负责：

- 决定是否应该发
- 决定是否应该先搜索
- 决定是否应该查历史

这些必须前置到心跳层。

------

二、你提到的两个场景，如何流畅实现

问题核心在于：如何在一个连续节奏中，不显得机械，同时又保持速度。

先明确一个原则：

心跳系统不应该“阻塞式等待对话模块结束”。
 它应该进入“行动占用状态”。

引入一个状态机：

GlobalState:

- idle
- executing_action
- cooling_down
- suspended_by_chat

当心跳系统触发一个 chat_reply plan 后：

1. 标记 executing_action
2. 进入 suspended_by_chat（标记本轮 normal loop 不再调度其他高成本行动）
3. 允许 fast loop 继续运行（健康检查 + 轻量判断）

这样：

对话模块执行期间，心跳不是休眠，而是降频。

------

三、关于真实性不足与速度问题

真实性来自三个因素：

1. 节律分离（多频心跳）
2. 行动预算限制
3. 决策记忆

你当前缺的是第三个。

你提到：

“前 n 次心跳元信息”

这不是可选项，而是必须内建。

否则每一轮决策都是“短视的即时反应”。

建议在 State Fabric 中增加：

DeliberationHistory:

- 最近 N 次 plan
- plan 执行结果
- 上次触达某对象时间
- 最近连续主动行为次数

然后在评分函数中加入：

interruptiveness_penalty
 recent_action_penalty
 target_fatigue_penalty

这样可以自然防刷屏。

------

四、Intent 与 Reply 的真正关系

你的模糊点来自一个错觉：
 “回复”看起来像一种意图。

实际上不是。

回复是 Action Type。

意图是：

- 冷场超过 30 秒
- 对某话题产生兴趣
- 某个记忆被触发
- 某个对象活跃度上升
- 有未完成话题

Intent 是“驱动力来源”。
 Reply 是“实现方式”。

如果你把 Reply 也当 Intent Provider，就会混乱。

正确方式：

IntentProvider 只生产抽象意图：

- engage_user
- explore_topic
- verify_fact
- follow_up_memory

然后 Planner 决定：

engage_user → chat_reply
 explore_topic → web_search
 verify_fact → tool_call
 follow_up_memory → memory_retrieve + chat_reply

这一步抽象非常关键。

------

五、关于联网搜索 + 保存 + 再发消息的流畅性

你现在可能是线性做法：

决策 → 搜索 → 等结果 → 再发

这会造成阻塞感。

更合理的方式是：

生成多阶段 Plan DAG。

例如：

Intent: explore_topic(X)

Plan Graph:

1. web_search(X)
2. summarize(result)
3. memory_update
4. optional_chat_reply

执行器不需要一次性跑完。

你可以：

- 执行 1
- 记录 receipt
- 生成新的 Intent: summarize_pending_search
- 下一个 normal loop 执行 2

这样节奏自然分层，不会一口气爆发。

------

六、速度优化的真正关键

速度不是模型推理速度，而是决策复杂度。

必须区分：

轻决策（rule-based）
 重决策（LLM-based）

建议：

fast loop:

- 纯规则
- 不调用大模型

normal loop:

- 只有当 candidate_plans 数量超过阈值才调用 LLM 评分

否则用轻量公式评分。

不要每轮都调用模型进行全局仲裁。

------

七、如何彻底解决“心跳和回复器的边界模糊”

建立一个不可违背的工程约束：

聊天模块永远不知道：

- 当前预算
- 当前是否冷却
- 当前是否有更高优先级计划

它只是执行器。

所有触发必须来自心跳。

你可以允许聊天模块返回“建议行动”，
 但它只能返回 SuggestionIntent，而不是直接执行。

SuggestionIntent 进入 Intent Queue，和其他意图一起仲裁。

------

八、你目前结构“差点意思”的真实原因

你现在的系统是：

单层认知循环。

真正的人类决策结构是三层：

即时反射
 当前目标规划
 长期目标维持

你的设计有多频心跳，但没有“长期目标容器”。

建议加入：

GoalRegistry:

- 短期目标（分钟级）
- 中期目标（小时级）
- 长期目标（天级）

IntentProvider 可以从 GoalRegistry 生成意图。

否则系统只会围绕当前上下文打转，缺乏纵深。

------

九、重新定位心跳系统

不要把它当作：

“定时触发器”

而要把它当作：

“带节律的全局仲裁调度内核”

聊天模块：

- 是 ActionAdapter.chat

搜索：

- 是 ActionAdapter.search

历史记录查看：

- 是 memory_retrieve 行动

它们没有本质区别。

------

十、总结你的优化方向

1. 把“是否行动”彻底从回复器剥离。
2. 引入执行态状态机，避免阻塞式休眠。
3. 用 DeliberationHistory 防止短视。
4. 引入 GoalRegistry 解决纵深不足。
5. 使用 Plan DAG 拆解复杂行动。
6. 轻重决策分层，减少模型参与频率。
7. SuggestionIntent 机制解决模块交叉。

当这些完成后，心跳系统就不再是“聊天触发器升级版”，而是一个真正的全局认知编排系统。

它会自然产生你想要的那种感觉：

不是快，而是稳。
 不是频繁，而是合理。
 不是能做很多事，而是每次做事都有结构与理由。
